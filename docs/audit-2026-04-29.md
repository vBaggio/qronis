# Auditoria Arquitetural — Qronis Modulith
**Data:** 2026-04-29  
**Contexto:** Análise pós-refatoração para monólito modular (Spring Modulith). Dissolução de relacionamentos `@ManyToOne`/`@ManyToMany` cross-module → referências por UUID puro.

---

## Status Geral

A migração para Modulith está **estruturalmente correta**: fronteiras de módulo respeitadas, Facades como único canal cross-module, sem violações de `ApplicationModules.verify()`. Os problemas encontrados são consequências colaterais específicas da dissolução dos relacionamentos JPA, não falhas de design.

---

## Problemas Encontrados

### 🔴 CRÍTICO 1 — N+1 Queries: `TimeEntryMapper`
**Arquivo:** `src/main/java/com/qronis/modules/tracker/application/TimeEntryMapper.java:24`  
**Status:** Aberto

**Causa raiz:** Antes do Modulith, `TimeEntry` tinha `@ManyToOne Project project` — o nome do projeto vinha via join/eager load. Após dissolução para UUID (`project_id`), o mapper resolve o nome via `projectFacade.getProjectName()` individualmente para cada entrada.

**Impacto:**
- `getProjectName()` implementado em `ProjectService.java:63` chama `projectRepository.findById()` — 1 SELECT por entry
- Para uma página de 20 `TimeEntry`: **1 query para entries + até 20 queries para nomes = 21 queries**
- Sem cache, mesmo projectId repetido dispara query duplicada
- Afeta: `GET /api/time-entries` (History) e `GET /api/time-entries?projectId=x` (ProjectDetails)

**Método afetado no mapper:**
```java
@Mapping(target = "projectName", expression = "java(projectFacade.getProjectName(timeEntry.getProjectId()))")
public abstract TimeEntryResponseDTO toResponse(TimeEntry timeEntry);

public abstract List<TimeEntryResponseDTO> toResponseList(List<TimeEntry> timeEntries);
```

**Fix recomendado:** `@Cacheable(value = "projectNames", key = "#projectId")` em `ProjectService.getProjectName()` + `@EnableCaching` em `QronisApplication`. Mantém fronteira de módulo, elimina queries redundantes para o mesmo projectId.

### 🔴 CRÍTICO 2 — Gap de Segurança: `patch()` não valida novo `projectId` contra tenant
**Arquivo:** `src/main/java/com/qronis/modules/tracker/application/TrackerService.java:79–99`  
**Status:** Aberto

**Causa raiz:** O `tenantId` é extraído do JWT e passado para `patch()`, mas nunca utilizado. Ao trocar o `projectId` de uma entry, nenhuma validação de tenant é feita.

**Código problema:**
```java
public TimeEntry patch(UUID id, TimeEntryPatchRequestDTO request, UUID tenantId, UUID userId) {
    TimeEntry entry = findByIdAndUserId(id, userId);
    // ...
    if (request.projectId() != null) {
        entry.setProjectId(request.projectId()); // ← tenantId ignorado
    }
}
```

**Vetor de ataque:** Usuário autenticado no tenant A envia `PATCH /api/time-entries/{id}` com `projectId` de um projeto do tenant B. A entry passa a referenciar um projeto de outro tenant — violação de isolamento.

**Fix:** Inserir `projectFacade.validateProjectBelongsToTenant(request.projectId(), tenantId)` antes de `entry.setProjectId(...)`.

### 🔴 CRÍTICO 3 — `NewProjectDialog` quebrado em `Projects.tsx`
**Arquivo:** `frontend/src/pages/projects/Projects.tsx:144–148`  
**Status:** Aberto

**Três bugs em cascata:**

1. **Caracteres corrompidos na linha 146:** `setOpen(false);ÍÍÍÍÍÍÍÍÍÍÍÍÍÍÍÍÍÍÍÍÍÍÍÍÍÍÍÍ` — pode causar erro de sintaxe dependendo do toolchain
2. **`setError(...)` dentro do `try`** (não no `catch`) — exibe mensagem de erro mesmo em criação bem-sucedida
3. **`onCreated()` nunca chamado** — a lista de projetos não atualiza após criar via dialog

**Código problema:**
```typescript
try {
    await api.post('/projects', { name: name.trim() });
    setName('');
    setOpen(false);ÍÍÍÍÍÍÍÍÍÍÍÍÍÍÍÍÍÍÍÍÍÍÍÍÍÍÍÍ    // linha corrompida
    setError('Não foi possível criar o projeto. Tente novamente.');
} finally {
    setLoading(false);
}
```

**Fix:**
```typescript
try {
    await api.post('/projects', { name: name.trim() });
    setName('');
    setOpen(false);
    onCreated();
} catch {
    setError('Não foi possível criar o projeto. Tente novamente.');
} finally {
    setLoading(false);
}
```

### 🟡 ALTO 4 — `createdByName` sempre `null` — Regressão de API
**Arquivo:** `src/main/java/com/qronis/modules/project/application/ProjectMapper.java:13`  
**Status:** Aberto

**Causa raiz:** Antes, `Project` tinha `@ManyToOne User createdBy` — nome resolvia via join. Após migração, a entidade tem apenas `UUID userId` (`created_by` no DB). O mapper foi ajustado com `ignore = true`.

**Impacto:** `ProjectResponseDTO.createdByName` sempre `null`. O frontend (`Projects.tsx`) tem `createdByName: string` no tipo TypeScript mas não renderiza o campo — visualmente não quebra, mas o contrato da API (`api.md` documenta `"createdByName": "Jane Doe"`) está violado.

**Opções de fix:**
- Remover `createdByName` de `ProjectResponseDTO` e do tipo TS (menor esforço, honesto com o estado atual)
- Adicionar `getUserDisplayName(UUID userId): String` em `IdentityFacade` e popular no `ProjectService`

---

### 🟡 ALTO 5 — `UserController.me()` lança `RuntimeException` bruto
**Arquivo:** `src/main/java/com/qronis/modules/identity/web/UserController.java:30`  
**Status:** Aberto

**Problema:** JWT válido com userId inexistente no banco retorna HTTP 500 com stack trace, fora do padrão `ErrorResponseDTO`.

```java
.orElseThrow(() -> new RuntimeException("Usuário não encontrado"));
```

**Fix:** Criar `UserNotFoundException` em `identity/domain/exception/` e tratar em handler específico retornando `ErrorResponseDTO` com status 404.

---

### 🟠 MÉDIO 6 — `ProjectSelector.tsx` hardcoded `size=100`
**Arquivo:** `frontend/src/components/tracker/ProjectSelector.tsx:37`  
**Status:** Aberto

**Problema:** Tenants com >100 projetos têm lista truncada silenciosamente. O filtro de busca é client-side sobre os 100 carregados — projetos além do limite são invisíveis no timer e histórico.

**Fix:** Passar `searchQuery` para o backend (`?name=`) em vez de filtrar client-side. O backend já suporta esse parâmetro em `GET /api/projects`.

---

### 🟠 MÉDIO 7 — `TenantUserRepository.findByUserId()` — lazy loading trap
**Arquivo:** `src/main/java/com/qronis/modules/identity/infrastructure/persistence/TenantUserRepository.java:14`  
**Status:** Aberto

**Problema:** Método derivado sem JOIN FETCH. Acesso a `tenantUser.getUser()` ou `.getTenant()` fora de transação ativa dispara `LazyInitializationException`. Atualmente sem chamador na service layer, mas é armadilha para futuros devs.

**Fix:** Remover o método — `findByUserIdWithUserAndTenant` já cobre o caso de uso.

---

### 🔵 BAIXO 8 — `@Transactional(readOnly = true)` ausente em métodos de leitura
**Arquivos:** `ProjectService.java`, `TrackerService.java`  
**Status:** Aberto

Métodos `findByTenantId`, `findByUserIdAndOptionalProjectId`, `findActive`, etc., não usam `readOnly = true`. Priva o Hibernate da otimização de dirty checking.

---

### 🔵 BAIXO 9 — `GET /api/projects/{id}/time-entries` documentado mas não implementado
**Arquivo:** `docs/api.md` vs controllers  
**Status:** Aberto

Endpoint documentado em `api.md`. Não existe em nenhum controller. `TrackerService.findByProjectId()` existe mas não é exposto. Frontend usa `GET /api/time-entries?projectId={id}` como workaround — funciona, mas retorna apenas entries do usuário logado (não do tenant), o que pode divergir da intenção do endpoint original.

## Matriz de Impacto da Migração Modulith

| Dissolução | Consequência | Gravidade |
|---|---|---|
| `TimeEntry.project` → `UUID projectId` | N+1 no mapper | 🔴 Crítico |
| `Project.createdBy` → `UUID userId` | `createdByName` null | 🟡 Alto |
| FKs cross-module via DB constraint | patch() sem validação tenant | 🔴 Crítico |

---

## O que ficou correto

- Estrutura de módulos: `auth → identity`, `tracker → project + identity` — conforme design
- `@EmbeddedId TenantUserId` com `@ManyToOne` interno ao módulo `identity` — correto (não cross-module)
- `JOIN FETCH` em `findByUserEmailWithUser` e `findByUserIdWithUserAndTenant` — evitam N+1 no fluxo de auth
- `open-in-view: false` — correto, força resoluções explícitas
- `ddl-auto: validate` — correto para produção
- Unique index `idx_time_entry_active_per_user` no banco — garante regra de 1 timer ativo no nível DB
- Handlers por módulo com `basePackages` restrito — isolamento de tratamento de erro por bounded context
- `CAST(:projectId AS uuid)` na native query do sumDuration — necessário para PostgreSQL com parâmetros UUID
